## Transport decision needed

Four options are on the table. Each is scored only on evidence in this tree.

1. **Same origin, canvas inside the root Next app, `/api/v1` over cookies.** One app after PR-01 (`PLAN.md:364`), one cookie session (`PR69:lib/auth/server.ts:213`), no CORS needed (`next.config.ts:7-75`), and the route helper already returns typed errors (`PR69:lib/api/v1.ts:96-143`). Cost: every canvas screen becomes a client fetch or a server-rendered page against routes that do not exist yet for most domains (only two v1 routes exist in PR69: `clients` and `session`, PR69 file list), and the PWA inherits the same origin for free. This is the only option that keeps `getViewer()` server-side (`PR69:lib/auth/viewer.ts:35-39`) usable for the gate at `PLAN.md:371`.
2. **Same origin, server actions for web plus `/api/v1` for mobile.** Fewer moving parts for web (`useActionState` is already the house pattern, `app/(tracker)/workspace/[workspaceId]/onboarding/onboarding-panel.tsx:288`), but D6 requires the HTTP route anyway (`icm/03-plan/DECISIONS.md:34-36`), so every mutation is built twice. It also cannot serve the Capacitor bundle, which has no Next server.
3. **Separate origins, canvas dev server keeps its own port and calls the API cross-origin.** This is today's shape (`frontend/package.json:5-8`, `RUNBOOK.md:58-59`) and it is the cheapest short-term wiring, but it needs CORS, `SameSite=None; Secure` cookies and an origin allowlist, none of which exist (`Access-Control` grep: zero; PR69 sets no `trustedOrigins`, `PR69:lib/auth/server.ts:158-172`). Better Auth would answer `403 INVALID_ORIGIN` on auth calls, the exact failure the boot check warns about (`PR69:lib/auth/server.ts:132-134`). It also contradicts PR-01 and would have to be undone in W3.
4. **Same origin for web, bearer token for Capacitor.** Web keeps cookies; the native shell sends `Authorization` and the bearer plugin resolves it (`PR69:lib/auth/server.ts:357`), and the viewer path already accepts either (`PR69:lib/auth/viewer.ts:17-24`). Cost: two auth paths to test, a token store that does not exist (`icm/05-build/AUTH-DECISION.md:99` records no Capacitor plugin), and refresh rotation deferred (`icm/03-plan/DECISIONS.md:113-122`). This is the only option that matches the plan's own mobile statement (`PLAN.md:2267`, `docs/mobile` does not exist yet).

Recommendation on evidence: option 1 plus option 4 for the native shell. Option 1 is already the plan's destination, option 4 is already the PR's plugin choice, and both avoid CORS entirely. Option 3 should be rejected now rather than discovered in W3. Option 2 should be limited to form posts that also exist as routes.

What is missing for any of them: a named owner for the client fetch layer (X1) and one convention for failure and loading (X5, X7). Neither appears in any card.

## Transport decision needed (final form, three options)

The four options above collapse to three real choices, because option 4 is the native half of option 1.

1. **Same origin, `/api/v1` JSON routes, cookie for web and PWA, bearer for Capacitor.** Matches PR-01 merging the canvas into the root app (`PLAN.md:364`), D6's rule that the mobile bundle uses only HTTP routes (`icm/03-plan/DECISIONS.md:32-36`), and PR #69's own setup: one `baseURL` (`PR69:lib/auth/server.ts:162`), `bearer()` plus `nextCookies()` (`pr69.diff:5398`), viewer accepts either credential (`PR69:lib/auth/viewer.ts:17-24`). No CORS for web. Cost: most domains have no v1 route yet (only `clients` and `session` in PR #69), Capacitor token storage is undecided (`icm/05-build/AUTH-DECISION.md:96,99`), and the native build will need CORS or a native HTTP layer for its `capacitor://` origin (UNVERIFIED: no Capacitor config exists in the tree to confirm the origin).
2. **Same origin, server actions for web, `/api/v1` for mobile.** Reuses the house pattern (`useActionState` at `app/(tracker)/workspace/[workspaceId]/onboarding/onboarding-panel.tsx:288`) and the error path just hardened in #91 (`components/trainingprogram/program-bookings.tsx:127-141`). Cost: D6 still requires the HTTP route (`DECISIONS.md:34-36`), so every mutation exists twice, and actions cannot serve a static Capacitor bundle.
3. **Separate origins, canvas keeps its own dev server and calls the API cross-origin.** Today's process shape (`frontend/package.json:5-8`, `icm/05-build/RUNBOOK.md:58-59`), cheapest to start. Cost: no CORS headers anywhere (`next.config.ts:7-75`), no `trustedOrigins` in PR #69 (`PR69:lib/auth/server.ts:158-172`), so auth calls fail with the `403 INVALID_ORIGIN` the boot check warns about (`PR69:lib/auth/server.ts:132-134`); it contradicts PR-01 and must be undone in W3.

Recommendation: option 1, with one shared fetch client owned by PR-W0 that also fixes the failure and loading convention (X1, X5, X7), and server actions only as thin wrappers over the same services.
