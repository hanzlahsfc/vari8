# Wiring spec: canvas screen to backend map

Status: reference for the wiring waves (PR-01, PR-W0 to PR-W10, PR-MSG and their model and service PRs). No decision in the "Open decisions" section is taken here.

## Purpose and how to use it

The canvas (`frontend/`) dictates every screen and every field; the database follows the canvas (`icm/03-plan/DECISIONS.md` D1, line 5). This file maps each canvas screen to its backend and to the PLAN.md wave that wires it, and lists every gap that stops a screen from being wired. The evidence lives in three inventories copied verbatim into `wiring/`: [coach.md](wiring/coach.md) (26 coach screens), [client.md](wiring/client.md) (10 client screens) and [shell.md](wiring/shell.md) (34 auth, onboarding, shell and transport items). Every row there is cited to file and line at the commit it names (`b5751ac`, re-checked at `5418755`). To wire a screen: find it in the screen index, open its inventory section, read the model gaps and open decisions that touch it, and check the owning PR section in `icm/03-plan/output/PLAN.md`. When this file and an inventory disagree, the inventory wins, because it carries the citations.

## How the numbers were counted

- Screens: coach and client screens are the rows of each inventory's own Summary table (`wiring/coach.md` section "Summary", `wiring/client.md` section "Summary"). Shell items are the rows of sections A to D of `wiring/shell.md` (9 + 7 + 9 + 9 = 34).
- Gaps: for coach and client screens, the per-screen "gaps" value of the Summary table, summed by hand: coach 205, client 74. Each shell item carries exactly one gap (`wiring/shell.md` Summary table: "Every one of the 34 items carries a gap"), so shell contributes 34. Total 313.
- Blockers: coach and client use the coach definition (needs a new model, a contract change or an owner decision first). Shell has no blocker column; here a shell item is a blocker (y) when its owner column is wholly UNASSIGNED, the nine items `wiring/shell.md` lists (A8, A9, O4, O5, O6, X2, X5, X7, X9). Recount: coach 13, client 8, shell 9, total 30.
- Discrepancy found while counting: the coach Summary footer states "15 y", but its rows mark only 13 screens y (1, 2, 5, 9, 10, 14, 15, 17, 18, 20, 23, 24, 25). This file uses 13. The 205 gap total recomputes exactly.
- Wave column: PLAN.md section heading lines for each PR at `5418755` (for example PR-W3 heading at line 1557). Inventories sometimes cite a line inside a section (PR-SV2 1226, PR-M4 630 and 875, PR-M6 970 to 981); those are normalized to the heading line. Program waves (W1 to W6) for shell items are from `icm/05-build/PROGRAM.md:14-19` as `wiring/shell.md` states them.
- Model gaps (G1 to G27), unowned items (U1 to U22 plus 24 shell rows) and decisions (O1 to O16) are numbered so each list can be recounted.

## Cross-cutting contract

Source: `wiring/shell.md` section D (X1 to X9), its "Refresh at 5418755" corrections, and "Transport decision needed (final form, three options)". The transport choice itself is open (O1); the facts below hold whichever option is chosen.

- Transport today: the canvas makes zero network calls; every screen reads localStorage (X1). There is no shared client, no base URL and no card that owns one (`grep "fetch(" icm/05-build/cards/*.md` returns 0). PR #69 supplies the server half: `lib/api/v1.ts:96-143` (auth, Zod params, workspace resolve, typed JSON errors). Only two v1 routes exist in PR #69, `clients` and `session`.
- D6 rule: every operation is one Zod-validated service exposed as versioned JSON, and the static mobile bundle uses only HTTP routes (`icm/03-plan/DECISIONS.md:32-36`). Server actions are allowed only as thin web wrappers over the same services (X2).
- Origin: after PR-01 the canvas lives in the root app, one origin. There are no CORS headers and no `trustedOrigins`, so a separate canvas origin fails with Better Auth's `403 INVALID_ORIGIN` (X4).
- Auth and session (PR #69): one `baseURL`, a 7-day cookie session, the bearer plugin last; `getViewerFromHeaders` accepts cookie or bearer and checks the user is ACTIVE. `getViewer()` is server-only, so a client component needs the session route or props from a server parent (X9). The session route returns user, workspace, role and a capability map (A9); nothing in the canvas consumes it yet. PR-01's instruction to read `lib/auth/session.ts` collides with PR #69 deleting that file; build order decides (A6). Capacitor token storage and refresh rotation are undecided (X3, PR-31 decision package only).
- Session failure: the server refuses non-ACTIVE users and returns JSON 401/403, but the canvas has no behaviour for a session that dies mid-edit: no redirect, no banner, no retry (A8), and no 403 surface (S9).
- Failure convention: a correct `safeCall` pattern exists, duplicated verbatim in four files (`app/(tracker)/workspace/[workspaceId]/dashboard/client-tasks-widget.tsx`, `client-habits-widget.tsx`, and the two staff panels under `clients/[clientProfileId]/dashboard/`). The booking crash is fixed and `app/error.tsx` and `app/global-error.tsx` now exist (#91). Open: one shared helper and a canvas convention (X5).
- Loading convention: no `app/loading.tsx`; the canvas's only loading strings ("Opening your workspace...", "Opening client tracker...") describe localStorage hydration and would be wrong during a failing fetch (X7).
- Dirty guard: the old dashboard editor uses `lib/dashboard/navigation-guard.ts:155-165` (link clicks, popstate, `beforeunload`, Navigation API) with a "Saved, newer edits pending" indicator. The canvas builder has none; PR-W9 ports that pattern (X6).
- Feature flags: every client surface is flag-gated and off by default; wiring PRs need the flags set for their parity runs, and no card lists them. PR-R3 collapses flags later (X8).
