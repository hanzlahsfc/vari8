## Parity failure analysis (pre-existing, environmental)

The parity step fails on this host for the unmodified base too: the same `npm run parity` on a detached checkout of `2595a74` (zero PR-31 changes) produces the identical `parity FAIL: 70 problem(s)` with matching magnitudes (e.g. `s10-appearance@1440 px=1723023 geom=0/0/138` in both runs). So the failure is not caused by this branch.

Observed evidence (not proven cause): the harness documents "bit-exact on the reference host; env PARITY_AA_TOLERANCE for other hosts" (`tools/parity/run.mjs` header), and `compare.mjs` counts any geometry move over `MOVE_PX = 0.5`. Every FAIL line shows `text=0` with `geom=0/0/N` moves confined to `dx`/`dw`; for `s10-appearance@1440` all 160 moved elements have `dy=0`, `dh=0` and sub-pixel horizontal shifts. A font-metrics or rasterization difference between this host and the baseline host is the most plausible explanation, but it is unproven: the baseline records no host OS, and identical candidate/base failures establish only that this branch does not introduce the diff. The gate remains unresolved pending a reference-host run or an owner disposition.

Two remaining diffs that are semantic but owner-ruled: `Coach -> Owner` in the account block and `COACH WORKSPACE -> "Liliana Mansfeld Co…"` in the shell label are listed in `RULED` in `compare.mjs`; the workspace-name rule expects the untruncated `"Liliana Mansfeld Coaching"` while the render truncates with an ellipsis, which may also widen the diff count. Upstream question for the harness owner, not this card.

First-run failure (exit 2) was a different, fixed cause: `verify-local.sh` exports a random `AUTH_SECRET`; the app's instrumentation refuses when `AUTH_SECRET` and `.env`'s `BETTER_AUTH_SECRET` differ. Re-running with `AUTH_SECRET` exported equal to the `.env` value passed that point. Worth flagging to the pipeline owner as a lane-env footgun.
